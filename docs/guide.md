## How a decision is made

A task is assessed along any number of dimensions. There are two kinds:

- **score** dimensions are ordered levels, such as difficulty (Trivial to
  Expert) or duration (under 5 minutes to several hours).
- **choice** dimensions are categories, such as task type (implement, bugfix,
  refactor, review, research, ui, test, docs).

Each profile is an agent kind plus a model and effort, with a `point` on the
score dimensions it cares about and an optional `affinity` for choice options.
Routing has three steps.

1. **Inline overrides** are read and removed from the task text:
   - `@opus`, `@codex`, `@haiku`, and other aliases pin a profile. `@<profile-id>`
     also works, for example `@opus-high`.
   - `!hard`, `!long`, `!quick`, and similar shortcuts pin a dimension.
     `!<dimension>=<value>` also works.
2. **Assessment.** Every dimension becomes one question in a single System One
   request. By default this goes to [Jev](https://opencode.ai/docs/zen/) on
   OpenCode Zen (`jev-1.13-free`, no key needed), with a 5 second timeout. The
   answer is a probability distribution per dimension. If the call fails or the
   backend is disabled, keyword rules estimate difficulty, duration, and task
   type as single values. These rules understand English and Chinese only. When
   their confidence is below `scoring.min_confidence` (0.35), difficulty is
   raised one level. Other dimensions, such as scope, are left out in that case.
3. **Scoring.** Every available profile gets a penalty; the lowest wins.
   - Score dimension: `weight × E[under_penalty × max(0, task − point − tolerance) + over_penalty × max(0, point − task − tolerance)]`,
     measured in levels. `tolerance` (0.5) is a free zone around the point.
     A dimension missing from a profile's `point` costs nothing for that profile.
   - Choice dimension: `weight × Σ P(option) × (1 − affinity[option])`.
     Options not listed use `affinity["*"]`, or 1 if that is also missing. When
     the assessment has no answer for a choice dimension, a uniform prior is used
     so that specialist profiles do not win by default.
   - Plus `cost_weight × cost × agent_cost[kind]` (USD per task) and
     `time_weight × time` (minutes per task).

The default `under_penalty` is 4 and `over_penalty` is 0.5: sending a task to a
profile that is too weak costs much more than sending it to one that is stronger
than needed. Profiles that are disabled, or whose CLI is not on `PATH`, are
skipped. Ties go to the cheaper profile, then to the earlier one in the list.

`--profile` or an `@` alias pins a profile and skips the ranking. `--kind`
restricts the ranking to one agent kind. `--model` and `--effort` patch the
winning profile.

Policies from version 2 used ranges instead of points. They are migrated on
load: each range becomes its midpoint, and a full range becomes "does not care".

## The default policy

`config/policy.default.json` is generated by `tools/build_default_policy.py`
from [Artificial Analysis](https://artificialanalysis.ai/) data fetched on
2026-10-11. To change the default profiles, edit the data in that script and
regenerate; do not edit the JSON by hand.

- Dimensions: `difficulty` (5 levels, weight 1), `duration` (4 levels, weight 1),
  `scope` (4 levels, weight 0.5), `task_type` (choice, weight 6). The task type
  weight is high so that a type mismatch costs more than being a level or two
  away.
- Each model with an effort setting gets one profile per effort (low to max),
  drawn as a line on the routing map. Models run through OpenCode have no effort
  parameter and get a single profile.
- Difficulty is `(Intelligence Index − 30) / 7`. Duration follows the effort
  level: low 0.3, medium 0.9, high 1.5, xhigh 2.2, max 2.8.
- `cost` is the AA price per task in USD. `time` is the AA time per task in
  minutes for the model's tested effort, scaled by a common per-effort factor
  (low 0.35, medium 0.45, high 0.55, xhigh 0.64, max 1).
- `cost_weight` is 0.6 per dollar. `agent_cost` sets OpenCode to 0.25 because
  OpenCode Go is a flat subscription. `time_weight` is 0.01 per minute, mostly a
  tie-breaker.
- The policy has 34 profiles; 19 are enabled. All efforts are drawn on the map,
  but only the commonly useful ones route by default: Luna low/high, Haiku
  medium/high, Sonnet medium, Sol medium/high/xhigh, Opus medium/high/xhigh,
  plus the open models and the specialists. Enable the others in the editor.
- Three specialist profiles have a task type affinity of 1 for their own type
  and 0 for every other type: Codex with Sol for review, Sonnet for research,
  Cursor for UI. `codex-review` has no point, so its difficulty and duration
  cost nothing; `sonnet-research` has a duration coordinate (0.6), and
  `cursor-ui` has difficulty (1.5) and duration (1.0) coordinates.
- Every profile carries a `note` with the numbers it came from.

With these values, small mechanical edits usually go to inexpensive open models
through OpenCode (DeepSeek V4.1 Flash, GLM-5.3 Flash) or to Luna and Haiku,
most everyday work goes to GPT-6.1 Sol through Codex, and expert-level design
goes to Opus at high or xhigh effort.

The policy's `models` catalog lists each model's id in every agent that can run
it. For example GLM-5.3 is `opencode-go/glm-5.3` in OpenCode and `glm-5.3` in
Droid. In the editor, a selected profile shows a "runs in" switcher that
rewrites the profile's `kind` and `model` from the catalog. Colours follow the
model vendor, not the agent.

## Commands

```bash
herdr-router classify "<task>"                      # per-dimension distributions only
herdr-router route "<task>"                         # decision and top 3, launches nothing
herdr-router route "<task>" --json                  # full ranking with penalty breakdowns
herdr-router route "<task>" --no-systemone          # keyword rules only, no network
herdr-router route "<task>" --profile opus-high     # pin a profile
herdr-router route "<task>" --kind codex --effort high
herdr-router --policy draft.json route "<task>"     # try another policy file
herdr-router dispatch "<task>"                      # route and launch (inside Herdr)
herdr-router dispatch "<task>" --dry-run            # validate and preview only
herdr-router dispatch - < task.md                   # read the task from stdin
```

Other `dispatch` options: `--cwd`, `--name` (agent name), `--pane` (pane to
split), `--direction auto|right|down`, `--wait`, `--timeout <ms>`.

Every dispatch is appended to
`~/.local/state/herdr/plugins/herdr-router/decisions.jsonl`. The editor plots
these entries on the routing map.

## Dispatch and recovery

A dispatch splits a pane, starts the agent in it, and sends the task. It reports
delivery only after Herdr observes the agent `working` or `blocked`. A blocked
agent has received the task but may be waiting for your input.

`--wait` then waits separately until Herdr's default wait returns (the agent is
idle, done, or blocked). `--timeout <ms>` limits that extra wait. Neither
delivery confirmation nor the end of the wait means the task succeeded.

`dispatch --json` writes one JSON object to stdout on success. On failure it
exits 1, leaves stdout empty, and writes an error object to stderr. Both carry
`dispatch_id`, `stage`, `prompt_status`, `agent`, and `pane_id` when known; a
failure before an attempt starts has no dispatch id. Do not decide to retry from
the exit code alone.

| `prompt_status` | Meaning | What to do |
| --- | --- | --- |
| `not_sent` | No task was submitted, or Herdr rejected it before writing | Fix the error; check any pane that was left open before sending again |
| `unknown` | The task may have arrived, but activity could not be confirmed | Look at the named agent or pane; do not dispatch the same task again blindly |
| `confirmed` | Herdr saw activity after the task was sent | Do not resubmit; a later `--wait` timeout keeps this state |

The router never resends a prompt. If the first activity check stalls, it
watches for `working` or `blocked` once more without sending again. After a
failure or interruption, panes it created stay open and their ids are kept in
the decision log. A communication error during the split can leave a pane whose
id was never returned, so check Herdr before retrying.

Launch settings are checked before a pane opens: `dispatch.direction` is
`auto`, `right`, or `down`, and `dispatch.agent_start_timeout_ms` is an integer
from 1000 to 300000 (default 60000).

## Sessions and handoff

Every real dispatch, including from the popup, saves a session to
`sessions.sqlite3` in the state directory before opening a pane. The
`session_id` equals the attempt's `dispatch_id`. A session records the task,
route, working directory, phase, known agent and pane, and delivery state.
Older `decisions.jsonl` history is not imported.

```bash
herdr-router session list --limit 20
herdr-router session show <session-id> --json
# After checking the previous result, write decisions and remaining work to handoff.md:
herdr-router dispatch "review stage one and continue" --session <session-id> --handoff handoff.md --phase review --json
```

Continuing a session creates a new session and a new pane, linked by
`parent_id`. It inherits the parent's working directory and isolation mode; a
different `--cwd` or `--isolation` is rejected. The parent must have
`confirmed` delivery, which does not mean its work is finished, so check the
result yourself before continuing in the same directory. The previous agent's
conversation is not carried over.

The handoff file is copied into the session and the prompt, so editing it later
does not change this attempt. Only the new task text is used for assessment and
inline overrides; the handoff is appended after routing. `--handoff` can also be
used without `--session` for a fresh task.

Limits: the handoff must be an ordinary UTF-8 file of at most 48 KiB, and the
final prompt at most 64 KiB. `--handoff -` is rejected because stdin is reserved
for the task. `--phase` is a non-empty label of up to 64 characters.
`--dry-run` validates a continuation without creating a session or pane.
`session list` and `session show` do not load the policy or contact Herdr.

`status=in_progress` means the attempt has no final record; it does not mean an
agent is still running. A crash at the prompt step leaves `stage=prompt`,
`prompt_status=unknown`. Inspection never retries or guesses completion.

Session writes use short SQLite transactions and must succeed before work is
started or submitted. After activity is confirmed, a storage failure does not
change the delivery result or skip a requested wait; the output includes
`session_warning`. `session_store_busy` reports lock contention separately from
other storage errors.

## Worktree isolation

New tasks default to `shared`: the agent runs in the given directory and the
router does no Git inspection or checkout. Use a separate branch and working
tree when independent edits are worth the setup time:

```bash
herdr-router dispatch "implement the export feature" --isolation worktree --dry-run --json
herdr-router dispatch "implement the export feature" --isolation worktree --worktree-timeout 180000 --json
# Later stages reuse the same worktree and branch:
herdr-router dispatch "review the implementation" --session <session-id> --handoff handoff.md --phase review --json
```

`--dry-run` runs a read-only preflight and reports `create`, `reuse`, or
`shared`; it creates no session, branch, or directory. `--worktree-timeout` is
the total Git budget in milliseconds (default 60000) for inspection,
revalidation, checkout, and verification. It does not include task assessment.
Sessions record the measured `workspace.creation_ms`, including checkout hooks
and filters, but that is not a prediction for the next task.

Requirements for a new worktree:

- A committed `HEAD` and a clean source tree, with no uncommitted or untracked
  files. The router checks this before assessment and again before creating the
  worktree; on large repositories both scans take time.
- If you run from a subdirectory, it must exist in that commit; the worktree
  keeps the same subdirectory.
- Sparse checkouts, submodules, bare repositories, and repositories without a
  first commit are not supported yet.

Ignored files such as dependencies, caches, and environment files are not
copied, and the router runs no setup commands. Normal Git checkout hooks and
filters still run, so creation can involve network access. See the
[Git worktree documentation](https://git-scm.com/docs/git-worktree).

Worktrees live under the state directory at
`worktrees/<repository-hash>/<dispatch-id>`, outside the source repository. The
branch is `router/<dispatch-id>`; neither name contains task text. An existing
branch named `router` conflicts with this prefix and is rejected.

If the budget runs out after checkout starts, the router stops its Git process
group and reports `workspace.state=unknown` with the known path and branch. A
failure before checkout starts is recorded as `failed`. The router never falls
back to shared mode, retries, merges, pushes, or removes worktrees on failure.
Look at the error and session before cleaning up.

A continuation reuses the parent's worktree path and branch, keeping existing
edits and commits. It checks the worktree's identity but does not rescan for
dirty files. If the branch changed, the directory moved, or the workspace is not
ready, continuation stops. To change isolation, start a fresh task with a
handoff file instead of a parent session.

Worktree records are stored in the existing version-1 session database. Code
from before this feature cannot read those records, so keep a database backup
together with the matching code version if you roll back.

## Web editor

```bash
herdr-router ui                  # http://127.0.0.1:8765/?token=...
herdr-router ui --open           # same, and open the browser
herdr-router ui --lan            # also listen on LAN / Tailscale addresses; prints each URL
herdr-router ui --port 8796      # use another port
herdr-router ui --stop           # stop a background editor started by the plugin action
```

The editor is in English or Chinese, chosen from the browser language.
**Settings → Language** overrides that and is remembered in the browser.
Switching keeps the draft and trial results. Labels inside the policy stay as
written. Each section below links a full-page screenshot of that tab, taken
with the Chinese interface.

### Routing map and profile editor

Screenshot: [routing map and profile editor](../plans/ui-refresh-evidence/desktop-chart-editor.png).

The map plots profiles over any two score dimensions, filtered by task type.
The background shows which profile would win a task at each point, with thin
lines where the winner changes. It is computed on the server by the same
scoring code as the CLI: coarse while you drag, finer once you let go. Hover to
see the winner and runner-ups with their penalties.

- Drag a dot anywhere (it snaps to 0.05). Only the dimensions the profile has a
  coordinate on are changed.
- Hollow dots are specialists, dashed dots are profiles whose CLI is missing.
  A profile that ignores one axis is drawn as a dashed line along it; one that
  ignores both is listed under the chart.
- The side panel lists profiles by vendor with the share of the current map
  slice each one wins. 0% means another profile always beats it on this slice;
  it says nothing about real task frequency.
- Search and filters (enabled, disabled, missing CLI, zero coverage) narrow the
  list. Hiding a profile on the map does not disable it.
- Selecting a profile opens its editor: the agent it runs in, the model
  (from Claude aliases, `~/.codex/models_cache.json`, or
  `cursor-agent --list-models`), effort limited to what the model supports, a
  slider and number per dimension with a "does not care" switch, task type
  affinity, and advanced fields such as the prompt prefix.

### Dimensions

Screenshot: [dimensions tab](../plans/ui-refresh-evidence/desktop-dimensions.png).

Add, remove, reorder, or rename dimensions, and edit their question, levels or
options, and weight. Each dimension becomes one question to the assessment
model. When a dimension loses levels, points above the new top level move down
to it.

### Trial run

Screenshot: [trial run result](../plans/ui-refresh-evidence/desktop-trial.png).

Type a task (multi-line is fine; ⌘/Ctrl+Enter runs it) or pick an example. The
result shows the chosen model, agent, and effort, the penalty breakdown, and
how far ahead it is of the runner-up. Diagnostics show the distributions and the
full ranking, and the launch command can be copied. Trials use a snapshot of the
unsaved draft and never start an agent. Changing the task, assessment mode, or
policy marks an earlier result as stale.

### Settings and JSON

Screenshot: [settings tab](../plans/ui-refresh-evidence/desktop-settings.png).

Settings holds the penalty and cost knobs, the assessment backend, dispatch
direction and start timeout, `@` aliases, and `!` dimension shortcuts. The JSON
tab edits everything else directly.

### Saving

Undo and redo keep the last 100 draft operations; one continuous field edit or
drag counts as one. ⌘/Ctrl+Z and ⌘/Ctrl+Shift+Z work in policy fields (the task
box and JSON editor keep native text undo). **Discard changes** returns to the
last saved policy and can itself be undone. A summary lists changed profiles
and sections.

Saving validates the policy on the server, keeps the last 10 versions in
`policy.backups/`, and atomically replaces
`~/.config/herdr/plugins/config/herdr-router/policy.json`. Edits made while a
save is in flight stay unsaved. The CLI reads the policy on every run, so
changes apply immediately. If validation fails, the fields at fault are
highlighted.

A saved `policy.json` replaces the built-in default entirely, so profiles added
to the default later do not appear automatically. The profile list notes when
the default has profiles your saved policy lacks, and can add just those.

### Security

Every API request needs the token from the printed link. The first visit swaps
`?token=` for an HttpOnly cookie. Requests whose `Host` header is an unknown
domain are refused, which guards against DNS rebinding; use `--allow-host` for
another name. The editor can change launch arguments but cannot dispatch
agents.

## Herdr plugin actions

- `herdr-router.route` opens a popup. Type a task and press Enter to see the
  ranking, then press Enter again to dispatch. Type `k`, `m`, or `e` and press
  Enter to change the profile, model, or effort; `t` edits the task and `q`
  cancels. The popup closes about a second after a successful dispatch; a
  failure stays on screen with recovery hints until you press Enter. It exits
  on its own after 300 seconds of inactivity.
- `herdr-router.route-selection` does the same with the selected terminal text
  as the task.
- `herdr-router.open-editor` starts the editor in the background if needed and
  opens it in the browser. Its log is `ui.log` in the state directory.

Keybinding examples for `~/.config/herdr/config.toml` (choose unused keys,
then run `herdr server reload-config`). Linking the plugin registers its
actions; it does not add these bindings automatically:

```toml
[[keys.command]]
key = "prefix+d"
type = "plugin_action"
command = "herdr-router.route"

[[keys.command]]
key = "prefix+ctrl+d"
type = "plugin_action"
command = "herdr-router.route-selection"

[[keys.command]]
key = "prefix+shift+e"
type = "plugin_action"
command = "herdr-router.open-editor"
```

Press your configured Herdr prefix key first, then `d` to enter a task,
`Ctrl+d` to use selected terminal text, or `Shift+e` to open the editor. The
router targets the focused pane and its working directory. For selected text,
select it in the terminal before invoking the action; the popup starts with
that task ready for review.

## Policy file

The built-in default is `config/policy.default.json`. A user `policy.json`
replaces it as a whole.

The excerpt below illustrates the structure; it is not a complete policy.
Start from `config/policy.default.json` or the editor's JSON tab when making
your own policy.

```jsonc
{
  "dimensions": [
    { "id": "difficulty", "type": "score", "weight": 1, "instructions": "How hard…", "levels": ["Trivial…", "…"] },
    { "id": "task_type",  "type": "choice", "weight": 6, "instructions": "What kind…", "options": { "review": "…" } }
  ],
  "profiles": [
    { "id": "codex-review", "kind": "codex", "model": "gpt-6.1-sol", "effort": "high", "cost": 0.32,
      "affinity": { "task_type": { "*": 0, "review": 1 } } },    // no point: any difficulty / duration
    { "id": "sol-high", "kind": "codex", "model": "gpt-6.1-sol", "effort": "high", "cost": 0.32,
      "point": { "difficulty": 2.86, "duration": 1.5 } }          // dimension left out = does not care
  ],
  "scoring": { "under_penalty": 4, "over_penalty": 0.5, "tolerance": 0.5, "cost_weight": 0.6,
               "agent_cost": { "opencode": 0.25 }, "time_weight": 0.01, "min_confidence": 0.35 },
  "aliases": { "@review": "codex-review", "!hard": { "difficulty": 3 } }
}
```

To add a dimension, add it to `dimensions` and give the relevant profiles a
coordinate or affinity for it. No code change is needed; the assessment request
picks it up. The keyword fallback only knows difficulty, duration, and task
type, so a new dimension is ignored when the fallback is used.

Other backends that speak the same System One API:

- Paid `jev-1.13`: set `backend.model` to `"jev-1.13"` and export
  `OPENCODE_API_KEY` (or the variable named in `backend.api_key_env`).
- Local [Kev](https://github.com/jaredpalmer/kev): set `backend.base_url` to
  `"http://127.0.0.1:8009"` and `backend.model` to `"kev-latest"`.

`backend.include_repo_signals` is off by default; adding repository size to the
assessment made simple tasks look harder.

Agent flags, checked against each CLI's `--help`:

| kind | model | effort |
|---|---|---|
| claude | `--model` | `--effort low…max` |
| codex | `-m` | `-c model_reasoning_effort=…` (passed as-is; gpt-6.x supports up to max) |
| kimi | `-m` | `--thinking` / `--no-thinking` (low) |
| cursor | `--model name[effort=…]` | inside the model brackets |
| opencode | `mini -m provider/model` (the full TUI has no model flag) | none |
| droid | `--settings <state>/droid/<model>-<effort>.json`, written just before launch | `reasoningEffort` in that file |

`env.extra_path` in the policy is appended to `PATH` at launch, and `binaries`
maps a kind to its executable name (for example cursor to `cursor-agent`).

## Files and directories

| Path | Contents |
|---|---|
| `~/.config/herdr/plugins/config/herdr-router/policy.json` | Your saved policy; absent until you save in the editor |
| `…/herdr-router/policy.backups/` | The last 10 saved versions |
| `~/.local/state/herdr/plugins/herdr-router/decisions.jsonl` | One line per dispatch, including errors |
| `…/sessions.sqlite3` | Dispatch sessions and handoff snapshots |
| `…/ui-token` | Editor token |
| `…/ui.json`, `…/ui.log` | Background editor process info and log |
| `…/worktrees/` | Worktrees created with `--isolation worktree` |

When run as a Herdr plugin, `HERDR_PLUGIN_CONFIG_DIR` and
`HERDR_PLUGIN_STATE_DIR` override these directories.

Each machine has its own policy and history. To reuse a customized policy on
another machine, copy `policy.json`; sign in to the agent CLIs there separately.

## Troubleshooting

**A task went to an unexpected profile.** Run
`herdr-router route "<task>" --json`. `assessment.source` says whether the
assessment came from `systemone` or the keyword `heuristic`; for the latter,
`assessment.details.systemone_error` says why. `bumped: true` means difficulty
was raised for low confidence. Each `ranking[]` entry has a `breakdown` showing
which dimension or cost added the penalty. Decide whether the distribution is
wrong (reword the dimension's question or levels) or the coordinates are
(move the profile, change affinity, weight, or cost).

**Jev calls fail.** The free model needs no key. Network timeouts fall back to
keyword rules; raise `backend.timeout_s` if needed.

**`not_in_herdr`.** Dispatch must run inside a Herdr pane (`HERDR_ENV=1`). Use
`route` outside Herdr.

**`agent_not_ready`.** The agent is usually stuck on a startup prompt, such as a
trust-directory dialog or a Codex update notice. The pane and agent name stay
alive; run `herdr agent read <name>` to see the screen and answer it yourself.
An update prompt may change your global installation.

**A profile is "not on PATH".** Install the CLI, add its directory to
`env.extra_path`, or map the kind to the right executable in `binaries`.

**The editor says the token is wrong or required.** The link was cut off (narrow
panes wrap long URLs) or the server restarted with a new token. Run
`herdr-router ui --open`.

**`host not allowed`.** You opened the editor through a domain it does not
know. Start it with `--allow-host <name>`.

**Port 8765 is in use.** Check `lsof -iTCP:8765 -sTCP:LISTEN`, stop a background
editor with `herdr-router ui --stop`, or pick another `--port`.

**The popup seems stuck.** It exits after 300 seconds of inactivity. To end it
sooner, find it with `ps aux | grep "herdr-router popup"` and stop that process.

## Tests

```bash
python3 -m unittest discover -s tests -t .
node tests/test_frontend.js      # needs Node.js
```

The Python tests run offline and do not call Herdr. `tests/fixtures/` holds
recorded `jev-1.13-free` responses used as routing regression cases for the
default policy.
